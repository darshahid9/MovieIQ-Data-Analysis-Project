# MovieIQ — Predictive Analytics on Film Success

An interactive Streamlit dashboard that explores, tests, and predicts movie financial success
from budget, revenue, popularity, runtime, and rating data.

## Project structure

```
movieiq/
├── data/movies.csv          # source dataset
├── data_prep.py              # Stage 1 — loading & cleaning
├── eda.py                    # Stage 2 — exploratory analysis, saves charts to assets/
├── stats_tests.py            # Stage 3 — T-test & Chi-square test
├── train_model.py            # Stage 4 — Random Forest training & evaluation
├── MovieIQ.py                 # Stage 5 — Streamlit app (entry point)
├── model/movieiq_model.pkl   # trained model + genre encoder (generated by train_model.py)
├── assets/                   # saved chart PNGs
├── requirements.txt
└── README.md
```

## Run it

```bash
pip install -r requirements.txt
python data_prep.py      # optional: sanity-check the cleaning step
python eda.py             # optional: regenerate charts
python stats_tests.py     # optional: rerun the hypothesis tests
python train_model.py     # trains and saves the model (run once before the app)
streamlit run MovieIQ.py
```

## Stage 0 — Problem Statement

**1. What makes a movie "successful"?**
A movie is labeled successful if it earned more than it cost: `success = 1 if revenue > budget else 0`.
This is a simple, binary financial-profitability rule — it doesn't account for marketing spend,
inflation, or non-box-office revenue (streaming, merchandising), but it's a clean, reproducible label.

**2. Why is this valuable, and to whom?**
- **Studios / greenlight committees** — deciding which scripts to fund, and at what budget level, before production commits.
- **Investors / distributors** — deciding whether to co-finance a title or how wide a release to fund, based on estimated odds of recouping cost.

**3. Objective & steps.**
Objective: build a reproducible pipeline that cleans movie performance data, explains what drives
success, and produces a live success/fail prediction. Steps: (1) clean and label the data, (2) explore
relationships between features and success visually, (3) confirm which relationships are statistically
real vs. noise, (4) train and evaluate a classifier, (5) ship it as an interactive Streamlit app.

**4. Classification problem.**
This is binary classification: the target variable is `success` (0 = failure, 1 = success), a category,
not a continuous number. The model outputs a class label (and a probability) rather than a dollar amount.

## Stage 1 — Data Preparation

**1. Shape & summary stats.**
2,000 rows × 7 source columns (`budget, revenue, popularity, runtime, vote_average, title, genres`).
See `data_prep.py` output for full `.describe()` stats — budgets range ~$1.1M–$200M (mean ~$102M),
revenue ~$1.1M–$574M (mean ~$178M).

**2. Zeros in budget/revenue.**
A budget or revenue of exactly 0 is almost always a data-entry/missing-value artifact, not a real $0
film — and it would corrupt the success ratio (any revenue > 0 vs a 0 budget is an automatic, meaningless
"success"). This dataset happens to have **no zero or missing values** in either column, so no rows were
dropped, but the cleaning step (`data_prep.py`) still filters `budget > 0 and revenue > 0` defensively
for reuse on messier data.

**3. Target column & balance.**
`success = 1 if revenue > budget else 0` → **80.7% of movies are labeled successful**, 19.3% are not.
The dataset is **imbalanced** — a model that always predicts "success" would already be right 80.7% of
the time, which sets the bar the real model has to beat.

**4. Genre processing.**
The `genres` column arrives as a stringified list of dicts (TMDB format), e.g.
`[{'id': 18, 'name': 'Drama'}]`, not a pipe-delimited string. Each movie in this dataset carries at most
one genre. It's parsed with `ast.literal_eval` and reduced to a single `genre` string column (`"Unknown"`
for the 181 movies — ~9% — with an empty genre list), which is then usable directly for `groupby` and
sidebar filtering.

## Stage 2 — Exploratory Data Analysis

**1. Budget vs Revenue** (`assets/budget_vs_revenue.png`) — correlation **0.76**. Higher budgets do
trend with higher revenue, as expected (bigger films get bigger marketing/distribution pushes), but the
scatter is wide — plenty of high-budget films land below the success line too.

**2. Genre trends** (`assets/genre_trends.png`) — genre counts are fairly even (~190–220 each), and
success rates by genre are all clustered tightly between **78.5% (Sci-Fi) and 82.2% (Drama)** — a ~3.7
point spread that, as Stage 3 confirms, isn't statistically meaningful.

**3. Popularity / runtime / vote_average vs success** (`assets/feature_vs_success.png`) — of these
three, **popularity** shows the clearest (if still modest) separation between successful and
unsuccessful movies; runtime and vote_average show almost no visible separation.

**4. Correlation heatmap** (`assets/correlation_heatmap.png`) — the only strong pair is
budget↔revenue (0.76), which is expected and not a modeling concern by itself. The more important
finding: **popularity, runtime, and vote_average all correlate with `success` at roughly ±0.02–0.05** —
essentially noise. Even `budget` alone barely correlates with `success` (-0.03); revenue is the only
real driver, and revenue can't be used as a model input since it's literally how the target is defined
(that would be leakage).

## Stage 3 — Statistical Testing

**1. T-test — popularity vs success.**
H0: mean popularity is equal for successful and unsuccessful movies.
Result: t = 2.06, **p = 0.040** → below the 0.05 threshold, so we reject H0. Successful movies average
slightly higher popularity (50.7 vs 47.4), a real but small effect.

**2. Chi-square — genre vs success.**
H0: genre and success are independent.
Result: χ² = 1.77, dof = 9, **p = 0.995** → fail to reject H0. Genre has essentially no statistical
association with success in this data — the small differences seen in the EDA bar chart are noise.

**3. What a p-value means.**
A p-value is the probability of seeing a difference at least this large *if the null hypothesis (no real
effect) were actually true*. A small p-value means the observed pattern would be unlikely under pure
chance, so we treat it as evidence of a real effect. Threshold used: **α = 0.05**, the standard convention
— below it, we call the result "statistically significant"; it's a convention, not a law of nature.

## Stage 4 — Predictive Modeling (Random Forest)

**1. Features used.**
`budget, popularity, runtime, vote_average, genre_encoded`. **Excluded:** `title` (a unique
identifier, no predictive signal, would just cause overfitting/memorization) and **`revenue`** (it's
literally used to define the target — including it would be direct label leakage, giving artificially
perfect and meaningless accuracy).

**2. Train/test split.**
80/20, stratified on `success` to preserve the 80.7/19.3 class balance in both splits. A held-out test
set is essential because evaluating on training data would just measure memorization, not generalization
to movies the model hasn't seen.

**3. How a Random Forest predicts.**
It trains many decision trees, each on a bootstrapped sample of the data and a random subset of
features at each split, then lets every tree "vote" on the outcome — the majority (or averaged
probability) becomes the final prediction. Averaging many decorrelated trees reduces the overfitting
any single tree would have.

**4. Evaluation.**
Accuracy: **71.8%**, Precision: **80.2%**, Recall: **86.4%** (on the "success" class).
Confusion matrix: `[[TN=8, FP=69], [FN=44, TP=279]]`.
**Important finding:** 71.8% accuracy is *below* the 80.7% naive baseline of always predicting
"success." The model (trained with `class_weight="balanced"` to counter the imbalance) trades some
overall accuracy for slightly better minority-class recall, but it still misses most failures —
precision/recall for the "Failure" class are both low (~10-15%). Its biggest mistake bucket is false
positives: predicting success for movies that actually failed.

**5. Feature importance.**
Roughly even across `popularity` (0.25), `vote_average` (0.23), `budget` (0.23), `runtime` (0.20), with
`genre` trailing (0.10). This **agrees with the EDA and stats tests**: no single feature dominates
because none of them carries strong real signal — the near-uniform importances are a symptom of the
model grasping at weak/noisy features rather than finding one dominant driver.

## Stage 5 — Streamlit Dashboard

`MovieIQ.py` ships four tabs: **Overview** (KPIs + filtered table), **EDA** (all Stage 2 charts,
filter-aware), **Statistical Tests** (live T-test & Chi-square results), and **Predict a Movie** (form
→ live Random Forest prediction with confidence). Sidebar filters (genre, minimum vote average) drive
the Overview and EDA tabs. Verified locally with `streamlit run MovieIQ.py` (see repo — launches
cleanly, confirmed via headless smoke test).

**Deployment (bonus):** not deployed publicly in this pass. To deploy on Streamlit Community Cloud:
push this folder to a public GitHub repo, point Streamlit Cloud at `MovieIQ.py`, and make sure
`train_model.py` has been run at least once so `model/movieiq_model.pkl` exists in the repo (or add a
one-time training step to the deploy process, since Streamlit Cloud won't run arbitrary setup scripts
for you).

## Reflection

If a studio asked "Will our next film succeed?", I'd be **honest that MovieIQ's answer isn't reliable
enough to greenlight decisions on its own** — it performs *worse* than just guessing "success every
time." That's not a bug in the modeling; it's what the data supports: outside of revenue itself (which
can't be used, since it defines the label), nothing in this dataset — budget, popularity, runtime, or
rating — meaningfully predicts financial success. The statistical tests back this up directly.

**One limitation:** the dataset has no real causal drivers of success beyond revenue — it's missing the
features that would actually matter in practice (marketing spend, release date/season, star power,
franchise/IP status, competitor releases, critical reviews at launch, international vs domestic split).

**One improvement with more time:** engineer a `budget_tier` or `roi_potential` feature from historical
genre+budget-tier success rates, and pull in richer metadata (cast, franchise flag, release month) — the
current feature set is simply too thin for the model to do better than a coin flip weighted by the base
rate.
